The model — carrying provenance per field

Status: built. Written 4 Aug 2026 as a proposal; it is now model.py at the repo root, held by test_model.py. Solves the design problem raised in 00-multi-car-proposal.md, which should be read first. Kept as written — the reasoning is why the model has the shape it has.

The refactor needs one normalised model that both pipelines emit into: the M3's hand-maintained JSON and the Z4's parsed binaries. The proposal states the requirement — every field must say where it came from — and suggests generalising the Z4's confirmed / probable / candidate markers to do it. That is the wrong generalisation, for a reason worth stating before the schema.

Provenance and confidence are two axes

The Z4's markers do not describe values. Their own definitions, from e35_map.json:

confirmed — located by a controlled edit with a known before/after value
probable — location confirmed, but the field name or meaning is inferred
candidate — moved during an edit but not yet attributed to a specific field

Every one of those qualifies the offset, not the datum at it. All values the Z4 emits share a single provenance — a parser read them out of a file — and differ in how well the rule that decoded them is understood. Collapse the two and a hand-typed wire colour from a printed harness sheet becomes indistinguishable from a byte read through a guessed offset, which is exactly the distinction the model exists to preserve.

So each field carries two things:

origin — who produced the value.

parseda parser read it from a source. Re-running the parser reproduces it.
entereda human typed it from a document or off the car. Only that document can check it.
inferredthe pipeline computed it from other fields. Never authoritative; always recomputed.

confidence — how much you would bet on it: confirmed, probable, candidate, keeping the definitions already in the format maps but applied to the value.

They compose, and the composition is the payoff:

  • A parsed value's confidence is bounded above by the confidence of the offset that produced it. The format maps already carry that number, so they do double duty — they describe the format and rate every value read through them. Improve an offset from probable to confirmed by controlled edit and every car using that format gains confidence in that field, for free.
  • An entered value's confidence comes from its document. The RMod harness sheet at REV 01 is confirmed; something recalled at the car is candidate.
  • An inferred value takes the weakest confidence among its inputs.

Written as origin/confidence: parsed/confirmed, entered/candidate.

What origin is actually for

Rendering is the least of it. Origin answers three questions, and the second is the one that makes this non-optional:

  1. How is it presented? Confidence drives that, mostly — the Z4 renderer already colours by it.
  2. What may a rebuild overwrite? parsed and inferred fields are regenerated every build and hand-editing them is pointless — CONVENTIONS.md already warns that the next rebuild silently discards it. entered fields must survive re-parsing untouched. Without origin the builder cannot tell which is which, and merging the two pipelines means one file will hold both.
  3. What does disagreement mean? See below.

Disagreement is a finding, not a resolution

When two sources claim the same field, the model records both and emits a finding. It must never silently pick one.

cars/m3/schematic/build.py (apply_ecu) is already this, hard-wired for one case: it joins the calibration's assignments onto harness pins and reports unassigned / unwired rather than choosing. Generalise that function, not the markers. A parser producing a value where an entered one already exists is the most valuable event the pipeline can produce — it is the harness PDF being checked against the device — and it should read as a finding, not a merge conflict.

Field identity

Findings and provenance both need to name a field. One path scheme, dotted:

<car>.<device>.<group>.<item>.<attribute>
m3.m150.A.01.function
z4.pdm.output.12.trigger

Findings then carry the paths they reconcile rather than a display string, which is what lets the renderer link a finding back to its row.

Where provenance is written

Not inline on every value. {"v": "IAT plenum", "origin": "entered"} triples the size of m150.json and makes it unpleasant to hand-edit — and a human maintains that file by hand, every field, forever. That cost is not worth paying for information that is uniform across the whole file.

Declare it at the source and default it down; override per field only where it differs:

{
  "source": "harness-rev01",
  "provenance": "entered/confirmed",
  "connectors": [{"id": "A", "pins": [
    {"pin": 1, "designation": "AT5", "function": "IAT plenum",
     "wire": "Blue/gray", "resource": "Analogue Temperature Input 5",
     "prov": {"wire": "entered/candidate"}}
  ]}]
}

prov is sparse and absent on most pins. Existing data files gain two top-level keys and keep working — build.py reads pins with p.get(key), so an extra key is inert.

Sources are declared once in the car manifest, and a source is a device state, not a file:

"sources": {
  "harness-rev01": {"kind": "document", "path": "source/Ravin M3 harness pinout REV01 2026-01-18.pdf",
                    "obtained": "2026-01-18", "reflects": "as-built harness"},
  "m1-live":       {"kind": "device", "device": "m150", "obtained": "2026-09-14",
                    "how": "M1 Tune, Ethernet", "reflects": "as-flashed"}
}

reflects carries the as-file / as-flashed distinction that CONVENTIONS.md currently asks the commit message to carry. A config that exists in a file and a config that is on the car are different facts, and the model should hold that rather than leaving it in prose.

What this does not settle

  • Editorial flags. flag: crit|warn and the findings blocks are judgements, inferred by construction. Whether their confidence means anything, or whether they need a separate "who decided this" field, is unresolved.
  • Confidence on absence. A pin with no function may be genuinely unused or merely untranscribed. The M3 tables show both as —. Nothing above fixes it.
  • Whether parsed needs splitting by source kind — file versus live device read. Kept on the source rather than the field for now, on the argument that a parser does not care and a reader of the output will look at the source anyway. If that proves wrong it is an additive change.
