Proposal — one repo, many cars

Status: proposed, not built. Written 3 Aug 2026 at the end of the session that produced ravin-z4. Read this before starting the refactor.

What changed

ravin-m3 and ravin-z4 were built as separate repos. That was the right call for two cars with no shared tooling, and it is the wrong call for the actual requirement, which is: one repo you can add cars to, carrying the parsers to read whatever equipment each car has.

The decision to separate was made explicitly conditional on there being no third car. There will be more cars. This supersedes it.

The argument that settled it

The offset maps in schematic/data/ describe formats, not cars. e35_map.json is the layout of ECU Manager 3.5's file — it applies to any M800 in any car. c1212_map.json likewise. Kept in per-car repos they get copied and drift. Kept once, the second M800 car inherits the whole map for free, including every controlled edit already paid for.

Same for the renderer. The house style — the pin grid, the findings blocks, the confidence markers, the CSS — is currently duplicated between two build.py files that have already diverged.

Shape

garage/
  cars/<car>/car.json     manifest: which devices, which files, which overrides
             source/      exported configs, read-only
             data/        hand-entered facts no file contains
             docs/  schematic.html
  parsers/                one per FORMAT, never per car
    aim_zconf2.py  motec_pdm_xml.py  motec_c1212.py  motec_e35.py  motec_m1.py
  formats/                offset maps — shared format knowledge
  model.py                normalised: pins, channels, conditions, CAN, findings
  render/                 house style, written once
  tools/                  diff, audit, app
  build.py <car> | --all

The join is model.py. Parsers emit the normalised model; the renderer knows only the model and nothing about any car. Adding a car is then a manifest, plus one parser only if it brings a format nothing else has read.

The real design problem

The two existing pipelines are different shapes, and the refactor has to reconcile them rather than pick one.

ravin-m3/schematic/build.py renders from hand-maintained JSON. That is not laziness — the harness data comes from a PDF. No config file on that car contains wire colours or bulkhead routing, so a human types them in.

ravin-z4/schematic/build.py parses the source binaries directly and derives everything.

A car needs both: parsed facts and hand-entered facts, merged. The model must carry provenance per field — parsed, hand-entered, or inferred — because only the first is verifiable and the three deserve different treatment in the output. The Z4 schematic already does a weaker version of this with its confirmed / probable / candidate markers; generalise that.

A second source type to allow for

Sources here are files, but they need not be. MoTeC M1 Tune can read a resource map out of a live ECU over Ethernet, and that is the intended route for the M3's ecu_resources.json. Do not bake "a source is a file" into the model — a source is a device state, however it was obtained, and it should carry when and how.

What not to promise

"Add a car and the pipeline documents it" holds for formats already parsed. It does not hold for a new opaque one.

The axis that governs effort is structured vs opaque, not vendor. MoTeC .pdm is XML and took an afternoon. AiM .zconf2 parses. MoTeC .c1212v64 and .e35 are undocumented binaries that carry no field names at all, and everything known about them was won by controlled edit — change one setting in the vendor tool, save under a new name, diff. A new car with a new opaque format costs that again, whoever made it.

Why parse rather than read documentation

Three results from the session that produced this repo, all of which argue the same way:

  • The PDM operator codes are documented nowhere. They were recovered from the vendor's own sample configurations, which is a stronger source than a manual — those files were written by the software itself.
  • master.chl, the documentation-shaped route, gave confident wrong answers: per-cylinder lambda channels 3, 4 and 5 on a six-cylinder engine with two sensors. Parsing the file and anchoring to the car's own layout caught it.
  • The aux output encoding is a case where the documentation actively misleads. ECU Manager numbers the functions 0–9 then 101–129; the file stores the list position. Reading the manual and then the bytes maps every auxiliary output wrong. Only a known before/after from a real config revealed it.

Parse the device. Anchor to something car-specific. State the confidence.
