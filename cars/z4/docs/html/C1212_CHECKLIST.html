C1212 — what a controlled edit still buys

The four saves this checklist used to list are done, and none of them needs repeating: channel-to-pin binding, the alarm thresholds, the CHANL_D record layout and the CAN message layouts were all settled by reading the file. See the record layouts in the offset-map section of schematic/z4_pinout_schematic.html.

What is left is narrower. Three saves, in value order, and only the first is worth a trip on its own. The format is known to diff cleanly — GUID churn on save is understood and suppressed by the tool — so the method is no longer in question.

Protocol

  1. Always start from the same baseline copy of C1212 Alsense.c1212v64. Never chain edits.
  2. Give every field in a save a DIFFERENT value, so runs can be matched to fields by value.
  3. Write down what each field read BEFORE changing it — that is what decodes the field, not just locates it.
  4. Save As a new filename. Do not send to the dash.
  5. Run the diff after each save before moving on.

After each save:

python cars/z4/tools/diff_e35.py "cars/z4/source/C1212 Alsense.c1212v64" "cars/z4/source/<new>.c1212v64" --map formats/c1212_map.json --record "save 1 - display page"

Save 1 — Display page assignment — the only real gap left

Screens: Display / screen setup

The 46 field labels are located but their grouping into screens is inferred from a gap threshold, and nothing in the file marks a page boundary. Move ONE field from one page to another and the run that changes is the page reference.

FieldReads nowSet to
A display field (note which, and which page it is on)move it to another page

Save as Alsense PageTest.c1212v64.

→ A short run inside the label region means the page is a field in the label record, and all 46 resolve at once.

→ A run somewhere else means pages are a separate structure that references the labels, and that structure is what to map next.

Save 2 — CAN template flag bits

Screens: CAN / communications

+0x1FB4 upper bits and +0x1FB8 are undecoded. Direction no longer needs them — it falls out of which channel word is populated — so this is for rate and frame format only. Change a transmit rate on one template and the frame format on another.

FieldReads nowSet to
One template's transmit rateany other rate
One template's standard/extended settingthe other one

Save as Alsense FlagTest.c1212v64.

→ Both runs should land at +0x1FB4 or +0x1FB8 of the templates you touched, which assigns the bits directly.

Save 3 — Harvest a built-in channel id

Screens: CAN / communications — a transmit template

Now that word 9 of a +0x00EA record is known to be the source channel id, any built-in channel's id can be read off by putting it in a CAN message. This converts 'the id table is inside Dash Manager' into something answerable one channel at a time. Bind two built-ins whose ids are unknown to two free bytes of an existing transmit template.

FieldReads nowSet to
A free byte of a transmit templateunbounda built-in, e.g. Dig In 1 Speed
Another free byteunbounda different built-in

Save as Alsense IdTest.c1212v64.

→ Read word 9 of the two new records straight out of the rebuilt schematic — no diffing needed, the parser resolves them.

→ Repeat for as many built-ins as matter; each save is cheap.

Note. On the car, not in the tool: the PDM reads CDL3.Reverse Gear from 0x118 byte 6 and the dash's transmit template for 0x118 binds bytes 0, 2 and 4 only. Either bind reverse gear to byte 6 on the dash, or stop the PDM reading it. Note. Also worth fixing while you are in there, unrelated to mapping: 'RF Tire Pressure' and 'LF Tire Pressure' share the short name LFTP, so the two are indistinguishable on the dash and in the log tree. 'RR Tire Pressure' has no short name at all. Note. The C1212 has no maths channels. If you need a computed value on the dash, it has to be computed upstream — an M800 user channel or aux table — and sent over CAN.
