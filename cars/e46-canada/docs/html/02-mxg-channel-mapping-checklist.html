MXG 1.2 — settling which pin each channel is on

The claim under test. Ch0N in the configuration is Analog Input N on the connector, so Ch01 is pin 22, Ch02 is 26, Ch03 is 30 and Ch04 is 34. It is marked probable and lives in data/mxg-1.2-pinout.json under channel_mapping — that file is the source of truth for the status, and this one is the procedure. When an item below lands, both move in the same commit.

Why it is only probable. The pin functions come from the manufacturer's own sheet and are confirmed. Which sensor is on which channel comes from the configuration and is confirmed. That the two line up by number is neither: it is the obvious reading, taken because the device has exactly eight analogue inputs and the configuration names four channels Ch01–Ch04. Nothing in either file says so outright.

What it costs to be wrong. Someone traces a wire to the wrong pin. That is the whole exposure — no analysis in this repo depends on it, because every finding so far is about what a channel reads, not where it enters. It is worth one free reading and not worth a trip on its own.

What does NOT settle it

Listed so nobody spends a session on it.

  • Renaming a channel in RaceStudio 3 and diffing the export. That is the controlled edit this repo usually reaches for, and here it answers a different question. It would confirm which record in the .zconfig carries which Ch label — useful if the parser ever doubts itself, which it does not — and says nothing about pins.
  • Anything in either .xrk. The logs were checked. The channel table carries a name, a short name, a sample period, a width and a data type, plus the fid/typ fields, and none of them is an input index. A log records what a channel read, never where it entered.
  • The MXS 1.08 sheet or the out-of-production MXG page. Both are for other devices — see the note in mxg-1.2-pinout.json. The MXS disagrees with the MXG on the 22-pin connector's RS232 pins, which is exactly how a wrong-document mapping would look right and be wrong.

Protocol

  1. Item 2 is a reading, not an edit. Nothing is saved to the device and nothing is exported. If a session ends with a new .zconfig, something went wrong.
  2. Do not chain: reconnect each sensor before disconnecting the next, or two channels go open at once and the result names nothing.
  3. Whatever lands, update channel_mapping.status in data/mxg-1.2-pinout.json in the same commit, and say in the message which item settled it. The page reads its status from that file.
  4. If item 0 or 1 disagrees with item 2, the car wins and the disagreement is the finding — it would mean the dash is wired against its own convention.
